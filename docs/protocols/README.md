# Open Battle protocols

Everything Open Battle writes for someone else to read is a protocol: a file a player saves, a link another site makes, a message between browsers, a server's HTTP API, a rules package's manifest. Forks, mods, tools and other servers build on these, so each one has a version, a written spec, a machine-readable schema where it is JSON, and frozen test files that every later build must still read.

This page lists them all and sets the rules they share. Each spec page says what is special about its own.

## The rules every protocol keeps

1. **Every document says what it is.** Files carry `format: "open-battle/<name>@<major>"`. Other documents carry `v: <major>`. Peers announce `PROTOCOL` when they meet. A server API answers under `/v<major>/`.
2. **Readers ignore what they don't know.** An unknown field is skipped, never an error, so a newer writer can add one without breaking older readers. The schemas allow extra fields for this reason. A writer must not count on an older reader using a field it added.
3. **Within a major version, changes only add.** A new optional field, a new value where readers already skip unknown values, or a new message type that older peers ignore are allowed. Removing, renaming or retyping a field, making one required, or changing what a value means is a new major version.
4. **Readers keep reading every major they ever read.** Saved games, armies and replays are kept for years. A new major means a new reader beside the old one (or a conversion from old to new), never dropping the old one. The frozen fixtures in [`conformance/`](../../conformance) hold this in place.
5. **A newer major is named, not guessed at.** A reader given a major it doesn't know says the file came from a newer Open Battle (`newerFormat` in `src/share/links.ts`). It never opens a newer file the wrong way.
6. **Identity is by content.** Packages, assets, campaign books and shared files are named by the SHA-256 of their bytes. The same bytes always mean the same thing.
7. **The code is the source, the schema follows it.** Schemas are generated from the TypeScript types that read and write each format (`pnpm schemas`). CI fails when a type changes and its schema doesn't (`pnpm schemas:check`), so any change to a protocol shows up in review. Additive changes regenerate the schema. Breaking changes need a new major and a proposal ([GOVERNANCE.md](../../GOVERNANCE.md#changes-that-need-a-proposal)).

**Stability.** _Stable_ protocols follow all the rules above, and changing one needs a proposal. _Provisional_ ones follow the rules but may still get a new major after a short proposal while we learn. _Internal_ ones are not for outside use and may change in any release.

## Adding or changing a protocol

- **A new format:** give it `format: "open-battle/<name>@1"` (or `v: 1`), add its type to `SCHEMAS` in `scripts/schemas.mjs`, run `pnpm schemas`, add a sample to `src/protocols/samples.ts` and its reader to `READERS` in `src/protocols/protocols.test.ts`, then write its fixtures with `WRITE_CONFORMANCE=1 pnpm vitest run src/protocols`. Add a row here and a section to the spec page.
- **An additive change:** run `pnpm schemas` and commit the schema with the code. Say what was added in the spec page.
- **A breaking change:** a new major. Write a proposal first. Keep the old reader, give the new major its own schema file (`<name>.v2.schema.json`) and its own fixtures. Never edit or delete an old fixture.

## Conformance

[`conformance/`](../../conformance) holds frozen documents for each format and major. `valid/` documents must be accepted and `invalid/` ones turned away, both by the schema and by the app's own reader (`src/protocols/protocols.test.ts`). Another implementation can run the same files against its own reader and writer. See [conformance/README.md](../../conformance/README.md).
