OpenBattle design · Level 0 · Decision

ADR-029: The first rules package is Grimdark Future, and it suggests rather than acts

Status
Proposed Porter asked on 2026-10-17 to start a rules package implementing OnePageRules. Drafted the same day from the Grimdark Future game flow.
Context
ADR-001 left rules packages for later, and the engine now has what one needs: units, phases, priority, counters and marks, and items for weapons (ADR-025 to ADR-027), and line of sight (ADR-028). Walking a Grimdark Future game showed where the chores are: counting attacks, working out the number to hit and block after AP and cover, rolling, asking the other player to block and remove models, morale, and scoring objectives. The first attempt collapsed under a general package runtime with sandboxes, hooks and replayed scripts.
Decision
  • The first version ships one rules package, for Grimdark Future, as part of the app's own code. There is no way to load a package from elsewhere.
  • A game names the package it uses, by an action any player can take, and can turn it off the same way. Every browser in the game then runs it.
  • The package is a pure reading of the game: from the log (and the table it gives) it works out where the round is and offers suggestions. It keeps nothing of its own.
  • Suggestions hover over the unit they are about and open into the next choices one at a time (activate, then the action, then a target for each weapon type), with hints such as weapon ranges drawn lightly on the table. Picking is kept on the chooser's screen until a step takes actions or rolls.
  • It never acts on its own. A player clicks a suggestion, and their browser takes its actions as that player, through the same session as a hand-made move.
  • It asks the other player by handing them priority with a note, such as "Roll 7 blocks, 4+", and their browser offers them that step.
  • Every action may carry a note, so the log says why, such as "Failed morale: rolled 2, needed 4+".
  • It automates the core rules and the core special rules. Rules that only an army book defines are shown by name for the players to apply by hand.
  • It is built in slices, each proven in two real browsers before the next: stats from a list, then the round and activations, shooting, melee, morale, objectives and the winner, then spells.
Because
Suggestions keep "the app never refuses a move" and "a player can always override a package" true without any override machinery: the player simply doesn't click, or does it by hand. Two browsers each acting on their own would act twice; a click happens once. Reading only the log means a reload, a late joiner, a spectator and a saved file all agree on the step, and the game replays without the package (ADR-001). One package compiled into the app is the smallest thing that can help a real game, with none of the first attempt's runtime.
Rejected
A package that takes bookkeeping actions on its own, such as clearing marks at the end of a round: every browser running it would race to do it, and players would lose sight of what changed. A package runtime that loads code from a file or a link: the first attempt's road, and unsafe. A package with its own saved state: it would drift from the log after an undo or a hand-made fix. A package that checks moves and refuses illegal ones: breaks the first version's promise, and the players are the referees. Each browser choosing its own package: the two players would see different help, and the defender's browser wouldn't offer the blocks.
