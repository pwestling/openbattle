OpenBattle design · Level 1 · Decision

ADR-022: Each browser proves who it is with a key

Status
Accepted From the scaffold review on 2026-10-15. Accepted by Porter on 2026-10-15, "as long as it doesn't materially hurt player experience". Tightened on 2026-10-15 from the Record review: who signs, what a signature covers, and how ids are checked. The tightening (the log naming its link and host, signatures bound to the game's link, refused reused seals and empty signatures) was decided while Porter slept, at his request, for his review.
Context
A browser named its own id when it reached the relay, and every browser learned the others' ids. So anyone in a game could reconnect claiming to be the host or another player. And because the host writes the other player's dice value into the log, a host could change that value and steer a roll without the seal check noticing. Both defeat dice and draws nobody can fix.
Decision
  • On first use, each browser makes a key pair with the browser's own cryptography. The private half can never be read out of the browser. The browser's id is worked out from the public half.
  • A player's join puts their public key in the log, so every browser, spectators and saved files included, knows each player's key. The record refuses a join whose id is not worked out from its key, or whose key another player already has.
  • When two browsers connect, each signs a fresh random challenge from the other. A browser that cannot sign for the id it claims is refused. The relay still only introduces browsers; since 2026-10-16 (accepted by Porter) it also checks each browser's key as it joins, so nobody can take another's place there.
  • In a roll or a shuffled draw, the other player signs their random value, and the host must log the signature and who signed. The other player is the one rolling or drawing when that is not the host; when the host rolls or draws, it is a player who is not the host. The record refuses a value signed by the host, a missing or empty signature (unless the host took the roll or draw alone, ADR-023), and a seal already used earlier in the log. A host could still add a second seat of its own to sign with, but that seat joins in the log for everyone to see.
  • The signature covers who takes the action, the game's link, the kind of action, what is rolled or drawn (dice and sides, or deck and count, a roll's label and where the drawn cards go), the seal and the value, so it cannot be reused for anything else. Every browser checks it as the action arrives, and when loading a saved game; a roll or draw whose signature does not check is shown to everyone as tampered.
  • Opening the game in a second tab of the same browser moves the seat to that tab; the older tab shows the game read-only.
Because
Nobody can pose as the host or as another player, and no browser, the host included, can change another player's dice value without everyone seeing it. It costs the player nothing they would notice: keys are made and used without asking anything, and checking a signature takes well under a millisecond.
Rejected
Trusting the connection among friends: stops mix-ups but not a player who wants to pose as the host. Sending the other player's value to every browser instead of signing it: browsers that join later, and saved files, could not check it. Accounts or a server that vouches for people: the server would take part in games.
Limits
Clearing the browser's data loses the key, and with it the seat in games already joined; that player can rejoin as a new player. Moving a key to another browser could come later. The host still orders every action and could refuse to log one; that is visible, as in ADR-008.
